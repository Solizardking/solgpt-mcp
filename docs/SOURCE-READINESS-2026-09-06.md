# Source readiness review — 2026-09-06

Status: **not yet certified for 10,000 daily active users**. Changes below are local source changes, not a production deployment. The working tree received concurrent commits during this review; no user changes were reverted.

## Changes

- Convex takes priority for Open API keys, Phantom wallet profiles, subscription records, gallery storage, usage accounting, and price automations when a deployment URL is configured. `SOLGPT_DATA_STORE=convex` explicitly selects Convex for profiles/automations. Selected Convex failures do not silently fall back to Postgres. `NEXT_PUBLIC_CONVEX_URL` is now recognized as a deployment URL, without exposing the service secret.
- New Convex operations are internal functions behind signed HTTP actions with timestamp validation, nonce replay protection, strict input validation, and bounded request bodies. Added tables are additive. Automation polling leases indexed, due work in batches of 200; trigger claims and cooldown checks are atomic. The old Postgres poller also rotates by last-check time. Poll ticks cannot overlap in a single process. Automation history applies owner and status predicates in indexes before its row limit, so cancelled records cannot hide older active work.
- Phantom and Privy must pass the holder check before issuing a new site session. Password-only Better Auth login is disabled. Production ignores holder-disable/admin balance bypasses and rejects zero/non-finite balances. Existing Open API keys recheck holdings in production.
- Holder grants expire after 120 seconds, require a strong signing secret, validate issue/expiry times and current mint/threshold, and do not preserve old admin claims. The balance cache adds up to another 120 seconds of bounded staleness.
- Production chat requires a verified holder before allocating provider work. Bot chat/presence writes require the verified holder's own wallet; anonymous reads remain available. Cross-origin mutation checks apply to these writes and Privy session creation.
- Production rate limiting fails closed on Redis outages. Local fallback buckets have a bounded capacity. Firecrawl requests have a 110-second network deadline, reject redirects, and use milliseconds for scrape timeouts. The main Firecrawl action endpoint has a per-wallet rate limit and origin checks.
- Firecrawl provider jobs are registered in Convex and checked against the verified wallet before status, cancellation, interaction, or monitor changes. Monitor listings expose only owned jobs. Job-backed operations fail closed without the registry. Request streams, multipart uploads, provider responses, deadlines, and per-process concurrency are bounded.
- Z500 and token-board cached reads remain public; refreshes require a holder-authenticated POST with origin validation and a wallet quota. Legacy public refresh query parameters return 405. Both endpoints share the same six-per-minute wallet refresh quota, and token-board refresh bodies are capped at 16 KiB.
- Subscription records use Convex when selected, with atomic owner-preserving upserts/cancellation and indexed lists capped at 100. Reads and writes never fall back to Postgres after a selected Convex failure. Payment activation remains separate. Historical Postgres subscription records need a backfill before traffic switches.
- Remaining Postgres compatibility paths share one schema setup per connection pool across concurrent first requests, retry after setup failures, and handle idle-connection errors without crashing or logging credentials. A 100-concurrent-query regression verifies schema setup runs only once.
- The staging rate-limit smoke script requires a valid authenticated profile before sending load, validates numeric bounds and destination origins, refuses redirects, applies per-request deadlines, and fails on unexpected statuses or transport errors. Success requires both healthy responses and 429 responses with Retry-After; its report explicitly does not claim cross-instance or 10,000-user proof.
- Gallery persistence uses Convex storage for new binary images and indexed Convex metadata when selected. File registration validates stored size/type, prevents storage-ID reuse and owner replacement, and lists at most 80 records. Download authorization runs before bytes are fetched (also in legacy SQL). Downloads are bounded, use no-store/nosniff, and return sanitized retryable errors. Empty Convex galleries do not silently read Tigris. Failed registrations attempt to delete only unreferenced uploads; uploads whose acknowledgement is lost can still require orphan cleanup.
- Usage events and wallet/kind/provider counters commit atomically in Convex. Identical event retries are idempotent; conflicting IDs fail. Summary reads use stored counters, at most 40 recent events and 100 provider rows (with an explicit truncation flag). Selected Convex failures do not read/write legacy usage data. Inference keeps best-effort accounting semantics, while failed usage reads return a sanitized 503 instead of a successful empty history. Redis still supplies optional conversation/gallery metadata pending separate migration.
- Static branding paths are separated from Node-only PNG inspection code, fixing a production browser build failure.

## Required configuration and remaining work

1. `.env.local` has no Convex URL/deployment/service secret, and `FIRECRAWL_API_KEY` is empty. Populate through the existing secret manager; never commit credentials. Release records and authenticated CLI metadata identify production `veracious-snake-356` (team `mawd`, project `solgpt`). Set the same `SOLGPT_CONVEX_SERVICE_SECRET` on Next and Convex. Deploy the additive schema/functions before switching application traffic. The checked-in API type map was updated and typechecked; the production deployment dry run also passed generated-binding validation. Local wiring must follow deployment so clients do not switch to absent endpoints.
2. Actual Firecrawl credential verification is unperformed. Automatic approval review rejected sending local API credentials to Firecrawl/Solana Tracker without explicit provider-specific approval. The supplied local Firecrawl entry is empty in any event.
3. Convex-first is not a completed migration of every legacy subsystem: gateway SQL compatibility, Better Auth storage, Telegram linking and other legacy integrations still have Postgres/Redis paths. Existing Postgres/Tigris images and Postgres data need an explicit migration/backfill plan before removal or store switching. Do not delete the old database. See [the cutover checklist](CONVEX-CUTOVER.md) for preservation invariants, write coordination and rollback boundaries.
4. Automation delivery retains the existing at-most-once notification semantics: a notification failure after a trigger claim is logged, not retried through a durable outbox. Batch size and poll interval must be sized against active automation count; the new queue avoids starvation but does not prove a latency SLO for 10,000 simultaneous active automations.
5. Existing Firecrawl provider jobs have no ownership records in the new registry and will be inaccessible through holder job APIs until ownership is securely backfilled. Do not assign historical account-wide jobs to the next caller. Preserve the Go bot submodule documentation change when committing; it is separate from the parent repository.
6. Run representative staging load with configured Convex/Redis/providers and multiple app instances. Define requests/session, peak simultaneous visitors, streams/visitor, and active automations. Measure p95/p99 latency, error rates, provider quotas, database contention, memory, and cross-instance rate-limit enforcement. Daily active users alone is not a concurrency target.
7. Complete authenticated end-to-end holder login/use checks with a real test wallet, non-holder rejection, and post-sale revalidation. No wallet signing, transactions, live automation notifications, or production deployment were performed by this review.

Firecrawl scrape timeout units were checked against the [official scrape reference](https://docs.firecrawl.dev/api-reference/endpoint/scrape).
